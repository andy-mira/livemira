# VideoSession

[English](README.md) | [简体中文](README.zh-CN.md)

`src/video-session.mjs` owns one HTMLVideoElement's URL, playback and decoded-frame observer. Configuration uses public `MediaConfig` through the declaration file. Set `crossOrigin` before source, default muted/loop/inline, preserve time on pause, restart only when requested. `stop` releases src/srcObject and callback; `dispose` also removes error listener and is idempotent. Assigned streams are detached but their tracks belong to the caller; the fixture explicitly stops its generator tracks.

`observeFrames` returns false when requestVideoFrameCallback is unavailable; no rAF timestamp is mislabeled as a newly decoded frame. CSS video still composites natively in that case. Callback numbers and mediaTime are video presentation diagnostics, not camera observation time or motion-to-photon measurements.

Playback rejection and lifecycle race tests use an injected fake video. They do not prove browser autoplay policy, audio silence, codec/CORS compatibility, or decoder resource baselines. The module has no third-party media or runtime dependencies.

Looping: `MediaConfig.loop` (default true) sets native `video.loop`; false lets the clip end and stay ended, never rewinding. Native looping is preferred. Because playback was observed stopping near the end of a finite clip on a phone (decodedFrames and currentTime unchanged, `paused=false`, no `ended`), an active looping session also runs one 400 ms timer that only acts near the end of a clip with known finite duration, after two consecutive polls with unchanged currentTime and decoded-frame count. It rewinds to 0 and calls `play` only if the element is paused/ended. An `ended` event does the same only when active, looping, actually ended and at the current clip’s end. Mid-clip slowness never rewinds; after 3 recoveries without observed progress the session stops trying. Play rejection uses the normal failure callback with no retry. Media errors, `pause`, `stop`, `configure` and `dispose` cancel the timer, so a grace-expiry pause cannot be followed by recovery. Diagnostics report `loop`, `ended`, `loopRecoveries`; renderer media telemetry adds these and `duration` as optional fields so older logs remain compatible. This is a compatibility fallback, not a proven Safari root cause; behaviour on the phone is unconfirmed.

WeChat playback recovery: `MediaConfig.wechatPlaybackRecovery` (`'auto'` default, or `'off'`). Native `video.play()` is always called first in the caller's stack. Only when it rejects with `NotAllowedError`, and only for an iOS (iPhone/iPad/iPod) WeChat (`MicroMessenger`) user agent read from the video's own `ownerDocument.defaultView.navigator`, `src/wechat-playback.mjs` makes one `WeixinJSBridge.invoke('getNetworkType')` whose callback calls the current video's `play()` synchronously. The bridge is read from the same window (waiting for `WeixinJSBridgeReady` if absent); the ready/callback wait is bounded by one 1500 ms timer, with no polling, retries, preload or element reuse. `play`, `pause`, `stop`, `configure`, `dispose`, a native media error, a hidden page/`pagehide` or a newer `play` cancel the pending operation: timers and listeners are removed, the cancelled `play` settles `false` promptly, late ready/callback events never play, and rejections are consumed. A final failure keeps the existing `playbackBlocked`/`error` event, so a direct-gesture `resumeFromGesture`/`retryFromGesture` remains the fallback. No new event types. Diagnostics (and renderer `mediaState.media`) add optional `playbackPath` (`'native'|'wechat-bridge'|null`, the most recently issued attempt, not proof of success) and `wechatRecoveryAttempts`; `playing`, time and decoded frames remain the truth. Basis: one iPhone WeChat 8.0.79 probe where a third media's native play was rejected and the bridge callback then started real playback. That is evidence for this context-recovery trick, not a guaranteed host API; behaviour on other WeChat versions/devices is unproven, and these Node tests use fakes and prove no real-device behaviour.

Control looping through the existing SDK interface; no UI is required:

```ts
engine.setTargetMedia('bird-01', { url: videoUrl, loop: true }); // default: repeat
engine.setTargetMedia('bird-01', { url: videoUrl, loop: false }); // play once
```

Calling `setTargetMedia` replaces the media configuration; include the URL when changing the loop setting.

First presentable frame (2026-10-12): `awaitPresentableFrame(callback)` is a one-shot readiness watch for the *current* media request, used by the renderer's loading mask and circular reveal. It never treats `loadedmetadata`/`canplay`/`readyState` alone as readiness. With `requestVideoFrameCallback`, the first presented-frame callback counts only if the element also has `readyState >= 2`, non-zero `videoWidth`/`videoHeight` and no error (`signal: 'video-frame-callback'`; payload `mediaTime`, `presentedFrames`, `decodedFrames`). Without that API the conservative fallback (`signal: 'time-progress'`) polls every 100 ms and needs the same checks, an unpaused element, `currentTime` strictly increasing across two consecutive polls beyond its value when watching began and, when `getVideoPlaybackQuality` reports a finite count, more decoded frames than at the start; it can fire up to about two polls after the real first frame and never before it. A newer call, `stop`, `configure`, a media error and `dispose` cancel the watch (an epoch makes stale host callbacks inert and the host callback/timer is cancelled); `pause` does not, so a hidden request resumes with the same watch. `retryFromGesture` reloads the element (readyState drops to 0), so the caller must re-arm the watch after it; the renderer does. Streaming needs no full download: `preload='metadata'` plus `play()` as before, and nothing waits for `canplaythrough` or the end of the download. The Node tests use fakes and prove ownership/cancellation rules, not real decoding.
